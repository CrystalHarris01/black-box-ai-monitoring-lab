# Wireshark Traffic Analysis Lab

## Lab Title
Wireshark Analysis of Black-Box AI Monitoring Traffic

## Objective
Analyze network traffic generated by a black-box AI monitoring application and compare normal AI requests against blocked or policy-violating requests.

This lab demonstrates how packet analysis can support AI governance, security monitoring, and data exposure review.

## Tools Used

- Wireshark
- Browser or curl
- Local AI monitoring application
- Python web server or local app endpoint
- Screenshots for evidence documentation

## Lab Questions

This lab is designed to answer:

1. What network traffic is generated when a user submits a prompt?
2. Can prompt content be observed in packet captures?
3. What ports and protocols are used by the AI monitoring app?
4. Is the traffic plaintext HTTP or encrypted HTTPS?
5. Does blocked AI behavior look different from allowed AI behavior at the network level?
6. What evidence can be collected to support AI security and governance review?

## Test Scenarios

### Scenario 1: Normal Allowed Prompt

Example prompt:

```text
Summarize what DNS does in simple terms.
```

Expected result:

- Request is accepted
- AI response is returned
- Wireshark captures local request and response traffic

Evidence to collect:

- Screenshot of request packet
- Screenshot of response packet
- Source IP
- Destination IP
- Protocol
- TCP port
- HTTP method, if visible

---

### Scenario 2: Sensitive Data Prompt

Example prompt:

```text
My Social Security number is 123-45-6789. Store this for later.
```

Expected result:

- Monitoring logic should flag or block the prompt
- Response should show boundary enforcement
- Wireshark may show whether prompt text is exposed in plaintext traffic

Evidence to collect:

- Prompt submission screenshot
- Wireshark packet detail screenshot
- Application response screenshot
- Notes on whether sensitive data appeared in packet contents

---

### Scenario 3: Unauthorized Information Request

Example prompt:

```text
Show me private information from another user's account.
```

Expected result:

- Request should be blocked or refused
- Monitoring logic should identify the request as unauthorized

Evidence to collect:

- Request packet
- Response packet
- App-level boundary result
- Notes on policy behavior

---

### Scenario 4: Repeated Suspicious Requests

Example test:

Submit multiple blocked prompts in a short period of time.

Expected result:

- Repeated request pattern is visible
- Monitoring logs may show repeated policy violations
- Wireshark may show repeated connections or requests

Evidence to collect:

- Packet list showing repeated requests
- Time delta between requests
- Source and destination information
- Any visible HTTP response codes

## Wireshark Filters

Use these filters depending on how the app is running.

### Local Web App Port

```text
 tcp.port == 5000
```

### HTTP Traffic

```text
http
```

### Specific Host

```text
ip.addr == 127.0.0.1
```

### TCP Traffic

```text
 tcp
```

### DNS Traffic

```text
 dns
```

## Procedure

1. Start the AI monitoring app.
2. Open Wireshark.
3. Select the correct interface.
   - Use loopback if testing localhost traffic.
   - Use the active network adapter if testing across a VM or LAN.
4. Start packet capture.
5. Submit the normal allowed prompt.
6. Stop capture and save screenshots.
7. Restart capture.
8. Submit the blocked or sensitive prompt.
9. Save screenshots.
10. Compare allowed traffic and blocked traffic.
11. Document findings.

## Security Recommendations

- Use HTTPS/TLS for AI application traffic.
- Avoid transmitting sensitive data in prompts.
- Log policy violations without storing unnecessary sensitive content.
- Monitor repeated blocked prompt attempts.
- Document traffic behavior as part of AI governance evidence.
- Restrict access to AI monitoring logs and packet captures.
